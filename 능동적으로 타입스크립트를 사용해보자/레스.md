# 능동적으로 타입스크립트를 사용해보자

레벨2를 마치고부터, 레벨3 이펙티브 타입스크립트 책을 쭉 읽는 동안 "[블로그에서 SEED의 코드에서 설계 의도](https://lessis.tistory.com/15)", "[쿠폰 도메인의 타입 설계를 복기](https://lessis.tistory.com/23)", "[유니온이 왜 배타적이지 않은지](https://lessis.tistory.com/26)", "[optional never가 실제로 무엇을 막는지](https://lessis.tistory.com/28)" 글을 작성했었고, 나름 주제는 생각보다 늘 비슷했다고 생각하고 있긴하다.

타입스크립트 문법을 많이 배우면서 알게된 이... 타입스크립트가 이것 저것 만들어 둔 것 중에서 가장 짧은 표기를 골라야 할까, 아니면 적기 전에 질문 하나를 먼저 던지면서 최선의 상황을 끊임없이 의심하면서 개발해야 할까.

스스로 워밍업부터... Pick과 Omit으로 시작해 보자.

```ts
interface User {
  id: string;
  email: string;
  nickname: string;
  password: string;
}

type PublicUser = Omit<User, "password">;
```

비밀번호 하나만 빼면 되니까 Omit이 가깝다. Pick으로 쓰면 셋을 나열해야 하고, 오늘 만들어지는 타입은 둘이 똑같다. 여기까지는 타입을 붙이는 사람의 판단이고 틀린 것도 없다. 그런데 반년 뒤 `User`에 `passwordResetToken`이 추가되면 어떻게 될까. Omit은 그것을 조용히 `PublicUser`에 포함시켜 버릴 것이고, Pick은 당연하지만 포함시키지 않는다. 두 표기의 차이는 길이가 아니라 **베이스에 필드가 늘었을 때의 기본값**이었다. Omit은 새 필드를 기본으로 내보내고, Pick은 기본으로 막은 뒤 나에게 결정을 요구한다.

이 차이를 알고 나면 타입을 적는 일이 다르게 보일 수도 있다고 생각한다. 타입은 지금 값의 모양을 설명하는 것이 아니라 **다음 변경이 어디서 실패할지를 미리 정하는 일**이다. 수동적으로 붙인 타입은 오늘의 값에 맞고, 능동적으로 설계한 타입은 내일의 변경이 어디서 터질지를 고른다. 그리고 터지는 자리에는 순서가 있다.

## 실패하는 자리에는 순서가 있다

1. 값을 만드는 그 줄에서 컴파일 오류가 난다. 편집기에서 바로 보인다.
2. 파생된 다른 파일에서 컴파일 오류가 난다. CI에서 보인다.
3. 런타임 경계에서 잡히고 지표에 남는다.
4. 런타임 어딘가에서 예외가 난다. 사용자 화면에서 터진다.
5. 조용히 틀린 결과가 나간다. 아무도 모른다.

앞에서 해결할 수 있을 수록 머리가 덜 아프다. 1번은 고치는 데 몇 초가 들고, 5번은 발견하는 데만 며칠이 걸리기도 한다. 능동적 설계를 한 문장으로 줄이면, 예상되는 변경 하나하나를 이 사다리에서 가능한 한 위로 끌어올리는 일이다. 아래는 그러려고 타입을 적기 전에 던지게 된 여섯 가지 질문이다. 앞의 둘은 무엇을 적을지를 묻고, 가운데 둘은 적을지 말지를 묻고, 마지막 둘은 제대로 적어도 컴파일러가 보지 않는 것을 무엇으로 볼지를 묻는다. 뒤로 갈수록 타입 하나로는 끝나지 않는다.

## 1부. 무엇을 적을 것인가

### 첫 번째 질문. 타입을 그대로 스키마를 받아쓴 것인가, 의식을 하면서 개발한 것인가

타입 설계는 앞으로 읽을 범위이지만 우선 지금까지 공부한 것을 바탕으로 연습해보자. 버스 도착 예측 서비스의 타입 파일에 이런 타입이 있다. 아래 코드는 노선의 차량 관측 상태이다.

```ts
export type ObservationState = "VEHICLES_PRESENT" | "NO_VEHICLES_OBSERVED" | "UNKNOWN";

export interface Observation {
  state: ObservationState;
  observedAt: string | null;
  staleAt: string | null;
}
```

`state`가 무엇이든 `observedAt`과 `staleAt`은 각자 null일 수 있다. 세 필드가 서로 남남이니 이런 값이 전부 통과한다.

```ts
{ state: "VEHICLES_PRESENT", observedAt: null, staleAt: null }
{ state: "UNKNOWN", observedAt: "2026-09-17T10:00:00+09:00", staleAt: "2026-09-17T10:05:00+09:00" }
```

차량을 관측했다면서 관측 시각이 없고, 관측한 적이 없다면서 관측 시각이 있다. 내가 이해한 도메인에서 관측 시각이 비는 경우는 `UNKNOWN` 하나뿐인데, 타입은 그 관계를 모른다. 내가 적은 적이 없으니까. 쓰는 쪽에서도 티가 난다. 실제 코드는 `state`가 `VEHICLES_PRESENT`인지 확인한 뒤에야 차량을 그리는데, 그 분기 안에서 관측 시각을 꺼내 쓰려 하면 `observedAt`은 여전히 `string | null`이라 null 검사를 한 번 더 써야 한다. 도메인상 절대 참이 될 수 없는 분기가 코드에 남는다.

```ts
export type Observation =
  | { state: "UNKNOWN"; observedAt: null; staleAt: null }
  | { state: "VEHICLES_PRESENT" | "NO_VEHICLES_OBSERVED"; observedAt: string; staleAt: string };
```

관측을 했는지 안 했는지로 갈랐다. 이제 관측했다면서 시각이 없는 값은 만드는 줄에서 컴파일 오류가 나고, `state`를 확인하는 순간 `observedAt`이 `string`으로 좁혀진다. 책이 타입 설계 장을 여는 첫 원칙이 이것이다.

> 효과적으로 타입을 설계하려면, 유효한 상태만 표현할 수 있는 타입을 만들어 내는 일이 가장 중요합니다. (p.182)

여기까지는 블로그 글에서 유니온 글에서 결제 수단 예제로 길게 다뤘던 이야기라 요점만 적었다. 이 글에서 더하고 싶은 것은 두 가지정도가 있다.

하나는 받아쓰기의 흔적을 알아보는 법이다. 같은 파일에서 좌석 정보는 처음부터 `kind`로 갈라 두었다. 관측만 평평하다. 둘 다 상태에 따라 있는 필드가 달라지는 같은 모양인데 왜 한쪽만 나눴을까. 좌석은 처음부터 두 종류라고 생각하며 짰고, 관측은 서버 응답 명세를 그대로 옮겨 적었기 때문이다. 명세는 전송 형식이라 관계를 평평하게 펴서 보내고, 그것을 필드 순서 그대로 옮기면 관계가 사라진다. **필드 순서가 명세와 같고 nullable 필드가 둘 이상 나란히 있는 타입은 받아쓴 타입일 가능성이 높다.** 이제는 그런 타입을 보면 필드 사이의 관계부터 묻는다.

다른 하나는 반대 방향의 실패다. 관계를 적는 도구가 손에 붙으면 관계가 없는 곳에도 적게 된다. 유니온 글에서 최소 주문 금액 조건과 특정 상품 조건을 배타로 묶었다가, 둘 다 갖는 쿠폰이 도메인에 실재한다는 것을 뒤늦게 본 이야기를 했었다. 있어야 할 선을 안 긋는 것과 없어야 할 선을 긋는 것은 반대처럼 보이지만 원인이 같다. 타입을 적기 전에 도메인을 묻지 않았다. 그래서 첫 번째 질문은 "관계를 적었는가"가 아니라 "받아쓴 것인가, 적은 것인가"이다. 적었다는 것은 도메인을 보고 판단했다는 뜻이고, 그 판단은 선을 긋는 쪽일 수도 안 긋는 쪽일 수도 있다.

사다리로 옮기면 이렇다. 평평하게 받아쓴 타입에서 불가능한 조합은 화면에서 조용히 틀리거나, 어딘가에서 null을 읽다 터진다. 관계를 적으면 값을 만드는 줄에서 막힌다.

### 두 번째 질문. 원본과 함께 자라야 하는가

도입의 Pick과 Omit으로 돌아오자. 여섯 달 뒤를 실제로 그려 보면 왜 이것이 길이의 문제가 아닌지 분명해진다. 설명을 위해 만든 가상의 타입이다.

```ts
interface User {
  id: string;
  email: string;
  nickname: string;
  password: string;
  passwordResetToken: string; // 비밀번호 재설정 기능이 붙으면서 추가
  internalMemo: string; // 운영팀 메모, 추가
}

type PublicUser = Omit<User, "password">;
declare const omitted: PublicUser;
omitted.passwordResetToken; // 통과한다. 응답에 그대로 실린다

type PickedPublicUser = Pick<User, "id" | "email" | "nickname">;
declare const picked: PickedPublicUser;
picked.passwordResetToken;
// ~~~~~~~~~~~~~~~~~~ Property 'passwordResetToken' does not exist
```

`User`에 필드를 추가한 사람은 `PublicUser`의 존재를 모를 수 있고, 안다고 해도 열어 보지 않는다. 추가만 했으니까. 그런데 Omit으로 만든 `PublicUser`에는 두 필드가 자동으로 들어가고, 컴파일 오류는 없고, 응답 스냅샷 테스트를 안 짜 뒀다면 그대로 배포된다. Pick이었다면 새 필드는 안 들어온다. 내보내고 싶으면 목록에 손으로 적어야 하고, 그 순간 아.. 이거 내보내도 되는지를 한 번은 생각하게 된다.

`lib.es5.d.ts`를 열면 둘의 관계가 나온다.

```ts
type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
```

Omit은 Pick을 감싼 것이고, 근본 차이는 `K`의 제약 하나다. Pick의 `K`는 `T`의 키여야 하고 Omit의 `K`는 아무 문자열이나 된다. 그래서 Omit은 오타도 못 잡는다. `pageContents`를 빼려다 `pageContent`라고 적으면 아무것도 안 빠진 채 원본과 똑같은 타입이 되고, 컴파일러는 초록불이다.

그래서 Pick의 귀찮음은 비용이 아니라 기능이다. 원본이 자랄 때마다 나에게 결정을 요구하는 것이 Pick이 하는 일이고, 그 결정을 대신 내려 주되 기본값을 "포함"으로 두는 것이 Omit이 하는 일이다. 허용 목록과 차단 목록의 차이는 보안에서는 오래된 이야기인데, 타입에도 그대로 적용된다는 것이 나에게는 새로웠다.

그렇다고 Omit이 틀린 도구는 아니다. 원본을 따라가는 것이 의도일 때는 Omit이 맞다.

```ts
type MyButtonProps = Omit<ButtonProps, "onClick"> & { onPress: () => void };
```

`ButtonProps`에 `aria-label`이 추가되면 `MyButtonProps`도 따라가는 것이 맞다. SEED의 스니펫 래퍼가 패키지 타입에서 `children`과 `asChild`만 빼고 전부 물려받던 것이 정확히 이 자리였다. 밖으로 나가는 타입은 Pick, 원본을 물려받는 타입은 Omit. 질문은 "어느 쪽이 짧은가"가 아니라 **"이 타입은 원본과 함께 자라야 하는가"**이다.

이 질문이 재미있는 것은 파생 타입에서 끝나지 않는다는 점이다. 같은 축이 세 층위에서 반복된다.

파생 데이터. SEED의 `ResultSection` 스니펫은 size variant마다 적용할 레이아웃 props를 표로 묶는다.

```ts
const textContainerProperties = {
  large: { gap: "x3", pb: "x7" },
  medium: { gap: "x2", pb: "x6" },
} as const satisfies Record<NonNullable<ResultSectionProps["size"]>, VStackProps>;
```

키 타입을 variant에서 인덱스 접근으로 가져오니, variant에 값이 하나 추가되면 이 표가 그 키를 채우지 않는 한 컴파일 오류가 난다. 표가 원본을 빠짐없이 따라가도록 타입이 강제한다.

파생 로직. 쿠폰 글의 `assessCoupon`은 switch의 default에서 `coupon`을 `never`에 할당한다.

```ts
default: {
  const _exhaustive: never = coupon; // 새 discountType 추가 시 컴파일 에러
  return _exhaustive;
}
```

네 종류를 전부 처리했으면 default에 도달한 `coupon`은 `never`라 통과한다. 다섯 번째 멤버가 추가되면 그 멤버가 `never`에 할당되지 않아 정확히 이 줄에서 오류가 난다. 에러 위치가 곧 "여기 처리 안 했다"는 안내다.

셋은 도구가 다르지만 답하는 질문이 같다. 원본이 자랄 때 파생은 어디서 알게 되는가. Omit은 알지 못하고 조용히 따라간다. Pick은 파생 선언에서 손으로 결정하게 한다. `satisfies Record`와 `assertNever`는 파생이 있는 파일에서 컴파일 오류로 알린다. 원본에 손대는 사람이 파생의 존재를 몰라도 컴파일러가 대신 찾아가서 알려 주는 것, 그러니까 사람의 기억력을 신뢰 목록에서 빼는 것이 이 질문의 목적이다.

## 2부. 적을지 말지

### 세 번째 질문. 이 제약이 깨질 생성 경로가 실제로 있는가

관계를 적는 도구가 손에 붙으면 다음 문제는 과잉이다. 지난 글에서 판별 유니온 여섯 개에 optional never를 넣었다가 열아홉 줄 중 열여덟 줄을 도로 지운 이야기를 했다. 여기서는 그 결론이 사다리의 언어로 무엇이었는지만 적는다.

optional never는 다른 갈래의 키를 `?: never`로 선언해서 그 키에 어떤 값이 와도 막는 장치다. 유니온 글에서 배타성을 만드는 전략으로 소개했고, 그 문장은 지금도 맞다. 그런데 실제로 넣고 컴파일러로 확인해 보니 여섯 곳 중 다섯 곳에서 아무것도 막고 있지 않았다. 값을 전부 객체 리터럴로 만들고 있어서, 초과 속성 검사가 이미 막고 있었기 때문이다.

```ts
type Bare = { kind: "boarding"; level: SeatLevel } | { kind: "passThrough" };

const literal: Bare = { kind: "passThrough", level: "high" };
//                                           ~~~~~ TS2353 초과 속성 검사가 잡는다

const wide = { kind: "passThrough" as const, level: "high" as const };
const viaVariable: Bare = wide; // 통과한다. 신선함을 잃어 검사가 꺼졌다
```

초과 속성 검사는 신선한 리터럴에서만 돈다. 변수에 담기면 꺼지고, 스프레드를 거치면 꺼지고, 서버에서 파싱된 값은 처음부터 신선하지 않다. optional never가 일하는 자리는 정확히 그 꺼진 구간이다. 그러니 질문은 "이 타입에 배타성이 필요한가"가 아니라 **"내 코드에서 값을 만드는 지점이 그 꺼진 구간을 실제로 지나가는가"**이다.

여섯 개 중 실제로 지나가는 곳은 한 군데였다. 공통 필드를 변수에 담아 세 갈래에서 스프레드로 펼치는 함수다.

```ts
export function toStopView(stop: StopState, vehiclesInService: number): StopView {
  const base = { sequence: stop.sequence, stopId: stop.stopId, name: stop.name };

  if (!stop.boardingAllowed) {
    return { kind: "passThrough", ...base };
  }
  // ...
}
```

경로가 있으니 optional never를 남기는 것도 답이었다. 그런데 이득이 스프레드에서 나온다면 스프레드를 없애는 것도 답이다. 키 세 개를 갈래마다 다시 적는 대신 반환값이 다시 신선한 리터럴이 되고, 초과 속성 검사가 다시 돌고, 선언과 함께 따라오던 비용도 사라진다.

비용이 있었다는 것이 이 이야기의 핵심이다. 아무것도 막지 않는 선언도 공짜가 아니다. optional never를 넣으면 그 키가 모든 갈래에 선언되므로, 갈래를 좁히지 않고 그 키를 읽는 코드가 컴파일을 통과하기 시작한다. 실제로 `??` 폴백 하나가 통과 정류장에 탑승 확률 라벨을 붙였고, tsc도 eslint도 잡지 못했다. `"level" in view` 같은 `in` 가드는 모든 갈래에 `level`이 있으니 가를 것이 없어져 좁히기를 멈춘다. 선언을 더 엄격하게 만들려고 넣은 한 줄이 타입 검사를 통과하는 경로를 만든 셈이다.

첫 번째 질문과 나란히 놓으면 대칭이 보인다. 첫 번째는 적어야 할 것을 안 적은 실패이고, 세 번째는 안 적어도 될 것을 적은 실패다. 둘 다 질문을 안 던진 결과다. 사다리로는 이렇다. 경로가 없는 제약은 아무 자리도 위로 올리지 못하면서 조용히 틀리는 경로를 하나 만든다. 경로가 있는 제약은 그 대입 줄에서 막는다.

### 네 번째 질문. 오늘 어떤 호출부가 더 안전해지는가

세 번째 질문이 "막을 것이 있는가"였다면 네 번째는 "돕는 것이 있는가"다. 쿠폰 도메인을 설계할 때 모든 결정을 한 질문에 회부했었다. 이 타입을 추가하면 오늘 당장 실제 호출부 하나가 더 또렷해지거나 안전해지는가.

필드 하나짜리 인터페이스가 시험대였다.

```ts
export interface MinimumOrderAmountRule {
  minimumOrderAmount: number;
}

export interface FixedCoupon extends CouponBase, MinimumOrderAmountRule {
  discountType: "fixed";
  discountAmount: number;
}
```

구조적 타이핑이라 `extends MinimumOrderAmountRule`이라고 쓰나 `minimumOrderAmount: number`라고 직접 쓰나 만들어지는 타입은 같다. 컴파일러에게는 아무것도 더해 주지 않는 인터페이스라, PR 리뷰어도 정확히 그 점을 짚었다. 그런데 이 인터페이스는 혼자가 아니었다.

```ts
type CouponWithMinimum = Extract<Coupon, MinimumOrderAmountRule>;
// => FixedCoupon | FreeShippingCoupon

function requiresMinimum(coupon: Coupon): coupon is CouponWithMinimum {
  return "minimumOrderAmount" in coupon;
}

export function assessCoupon(coupon: Coupon, ctx: OrderContext): boolean {
  if (isExpired(coupon, ctx.now)) return false;
  const orderAmount = calcOrderAmount(ctx.items);

  // 최소 주문 금액 게이트. 규칙을 가진 쿠폰은 전부 여기서 한 번에 거른다
  if (requiresMinimum(coupon) && orderAmount < coupon.minimumOrderAmount) return false;

  switch (coupon.discountType) {
    case "fixed":
      return true; // 게이트 통과로 충분
    // ...
  }
}
```

인터페이스가 있어야 타입 가드를 쓸 수 있고, 가드가 있어야 스위치 앞에 게이트를 둘 수 있고, 게이트가 두 case에 복제되어 있던 규칙을 한 곳으로 모은다. 사슬의 끝에 실제 코드 개선이 매달려 있다. 그리고 새 쿠폰 종류가 `MinimumOrderAmountRule`을 extends하는 순간, 최소 주문 금액이 없는 쿠폰 객체는 만들어지지조차 않는다.

```ts
const issued: FixedCoupon = { id: 1, code: "A", discountType: "fixed", discountAmount: 5000 };
//    ~~~~~~ Property 'minimumOrderAmount' is missing
```

5,000원 할인 쿠폰에 최소 금액이 빠져서 3,000원짜리 양말에 쿠폰이 걸리고 돈이 조용히 새는 실수는, 리뷰어의 눈이나 발행자의 기억력이 아니라 구조가 막아야 한다. 이 사슬이 그 실수를 발행하는 줄로 끌어올린다.

반대로 접은 것들은 전부 혼자였다.

| 접은 것 | 접은 이유 | 위로 올린 변경 |
| --- | --- | --- |
| `Pick<AmountRules, "minimumOrderAmount">` | 추려낼 큰 베이스가 없다. 우회 비용만 남는다 | 없음 |
| Record 라벨 맵 | 소비처가 없다. 망라성은 `assertNever`가 이미 준다 | 없음 |
| Record 디스패치 테이블 | 핸들러 입력이 단계 의존이라 시그니처가 균일하지 않다 | 없음 |
| `CouponByType<K>` | 제네릭 소비처가 없다 | 없음 |
| `DeepReadonly` | 서식지가 라이브러리 코드다. 읽기 비용만 늘린다 | 없음 |

전부 매력적이었고 전부 손에 익은 도구였다. 접은 이유는 하나로 모인다. 오늘 어떤 변경도 사다리 위로 올리지 못한다. 채택된 것들은 사슬로 연결되어 있어 어느 하나를 빼면 옆의 것이 근거를 잃고, 접은 것들은 혼자라 빼도 아무것도 무너지지 않는다.

리뷰어와의 대화에서 얻은 것도 이 언어로 다시 적을 수 있다. 리뷰어는 최소 금액을 가진 중간 base를 두는 쪽, 그러니까 쿠폰 유형을 추상화하는 쪽을 떠올렸고, 나는 정책을 추상화했다. 둘 다 발행하는 줄에서 막는다. 차이는 다음 변경이 "정책 추가"일 때 드러난다. 유형 계층은 정책이 하나일 때는 깔끔하지만 정책이 둘 이상 조합되면 조합 수만큼 중간 base가 필요해지고, 능력 인터페이스는 `extends A, B, C`로 조합이 평평하게 풀린다. 오늘은 같은 자리에서 막는 두 설계도, 다음 변경을 그려 보면 사다리를 유지하는 쪽과 내려오는 쪽으로 갈린다.

## 3부. 제대로 적어도 컴파일러가 보지 않는 것

### 다섯 번째 질문. 누가 이 값을 바꿀 수 있는가

앞의 네 질문은 무엇을 적을지를 다뤘다. 여기서부터는 제대로 적어도 컴파일러가 봐주지 않는 자리다. 리액트로 컴포넌트를 짜다가 이런 것을 만난 적이 있다.

```tsx
interface User {
  name?: string;
}

function Profile({ user }: { user: User }) {
  if (!user.name) return null;

  return <button onClick={() => alert(user.name.toUpperCase())} />;
  //                                  ~~~~~~~~~ 'user.name' is possibly 'undefined'
}
```

맨 위에서 이미 걸렀다. `name`이 없으면 `null`을 반환하고 끝인데, `onClick` 안에서는 또 `undefined`일 수 있다고 한다. 그때는 리액트 문제인 줄 알았다. 구조 분해로 바꾸니 오류가 사라져서 그냥 넘어갔고, 아이템 23을 읽고 나서야 우연이 아니었다는 것을 알았다. 리액트를 전부 걷어내도 똑같이 재현된다.

```ts
function greetLater(user: User) {
  if (!user.name) return;

  setTimeout(() => {
    user.name.toUpperCase(); // 'user.name' is possibly 'undefined'
  });
}

function greetLaterLocal(user: User) {
  const name = user.name;
  if (!name) return;

  setTimeout(() => {
    name.toUpperCase(); // 정상
  });
}
```

좁히기는 값이 아니라 이름에 붙는다. 그리고 그 이름이 객체 속성이면 좁혀진 상태는 지금 이 자리에서만 유효하다. `setTimeout`에 넘긴 함수는 언제 실행될지 모르고, 그 사이에 누가 `user.name`을 지웠는지 알 방법이 없으니 타입스크립트는 좁히기를 포기한다. `const name`은 이 함수 스코프 안에 갇혀 있어서 재할당 여부를 컴파일러가 전부 볼 수 있고, 그래서 콜백 안에서도 유지된다.

그런데 정반대의 자리도 있다. 콜백은 이렇게 깐깐하게 보면서 함수 호출은 봐준다.

```ts
function clear(user: User) {
  delete user.name;
}

function greet(user: User) {
  if (user.name) {
    clear(user);
    user.name.toUpperCase(); // 타입 오류 없음. 런타임에서 TypeError
  }
}
```

`clear`가 `name`을 지우는데 아무 말이 없고, 돌려 보면 당연히 터진다. 타입스크립트가 몰라서가 아니다. 원칙대로면 함수를 부를 때마다 좁히기를 되돌려야 맞는데, 그러면 호출 한 번마다 검사를 다시 써야 하고 아무도 그렇게 못 쓴다. 그래서 함수가 타입 정제를 무효화하지 않는다고 가정한다(p.152). 대부분의 함수는 인자를 건드리지 않는다는 확률에 건 것이고, 건드리는 소수는 컴파일러가 안 본다.

두 현상은 반대처럼 보이지만 같은 질문으로 모인다. **이 값을 누가 바꿀 수 있는가.** 컴파일러는 그 답을 모르니 콜백에서는 비관적으로, 함수 호출에서는 낙관적으로 가정한다. 능동적 설계는 그 답을 내가 정해서 시그니처에 적는 것이다.

함수가 인자를 바꾸지 않는다면 `readonly`로 받는다.

```ts
function clearReadonly(user: Readonly<User>) {
  delete user.name; // The operand of a 'delete' operator cannot be a read-only property
}

function motionSegmentFor(stopSequences: readonly number[]) {
  stopSequences.sort(); // Property 'sort' does not exist on type 'readonly number[]'
}
```

호출부는 가변 배열을 그대로 넘길 수 있어 비용이 없고, 함수 본문에서 실수로 `sort`를 부르면 그 줄에서 막힌다. 컴파일러가 안 보기로 한 "함수 호출 뒤"를 "함수 안"에서 대신 보는 셈이다. 책도 직접 작성한 함수가 매개변수를 변경하지 않는다면 `readonly`로 선언하라고 하면서, 변경하면서 생기는 오류를 막을 뿐 아니라 변경이 일어나는 코드를 찾기도 쉬워진다고 적는다(p.94~95).

여기서 내 프로젝트의 불일치를 하나 발견했다. `arrivalPolicy.ts`는 배열을 `readonly ApproachingVehicle[]`로 받는데, 같은 화면의 `liveVehiclePolicy.ts`에 있는 `motionSegmentFor`는 `stopSequences: number[]`로 받는다. 둘 다 입력을 건드리지 않는 순수한 계산인데 한쪽만 소유를 정했다. 지금 당장 문제는 없다. 그러나 책이 말하듯 `readonly`는 전파되는 경향이 있고(p.94), 반대로 안 붙은 곳은 나중에 `sort` 한 줄이 들어와도 아무도 모른다. 같은 프로젝트 안에서 같은 성격의 함수가 다른 답을 갖고 있으면, 그 답은 설계가 아니라 그날의 기분이다.

콜백까지 들고 갈 값은 지역 변수로 뽑는다. 대가는 있다. 지역 변수는 그 순간의 값을 복사한 것이라 원본이 바뀌어도 따라오지 않는다. 타입을 믿을 수 있게 된 대신 값이 낡을 수 있다. 책은 그래도 지역 변수 쪽이 낫다고 하고, 나도 그렇게 본다. 값이 어긋나는 것은 눈에 보이지만 타입을 못 믿는 것은 안 보인다.

한 발 더 거슬러 올라가면 이 문제의 시작은 `name?: string`이라는 선택적 속성이다. 선택적 속성이 없으면 좁힐 일도, 좁히기가 깨질 일도 없다. 책 아이템 37의 예가 이 글의 논지를 그대로 보여 준다. 단위 시스템 옵션을 기존 코드에 영향을 주지 않으려고 `unitSystem?`로 추가했더니, 넘기지 않은 호출부가 생기고 미터법 사용자가 영국식 단위를 보게 된다. 필수로 바꾸면 `unitSystem`이 들어가야 하는 모든 곳에 오류가 표시되는데, 책은 이렇게 적는다.

> 표시된 모든 오류를 하나씩 수정해야 하지만, 사용자로부터 불평을 듣는 것보다는 나은 선택입니다. (p.220)

정확히 사다리의 언어다. 선택적으로 만든다는 것은 실패 자리를 컴파일 오류에서 조용히 틀린 화면으로 내리는 결정이다. 사다리로 정리하면 이렇다. 질문을 안 던지면 함수 호출 뒤의 변경은 런타임 예외로 나타나고, 콜백의 possibly undefined는 반사적인 `?.`로 덮여 조용해진다. `readonly`는 변경 시도를 그 줄에서 막고, 지역 변수는 콜백 안의 타입을 지킨다.

### 여섯 번째 질문. 타입이 못 보는 자리는 무엇으로 막는가

마지막 질문은 앞의 다섯을 다 지켜도 남는 것을 다룬다. 타입스크립트의 설계 목표 문서에는 하지 않기로 한 것들의 목록인 Non-goals가 있는데, 3번은 무결한(sound) 타입 시스템을 만들지 않고 정확성과 생산성 사이에서 균형을 잡는다는 것이고, 5번은 런타임 타입 정보를 만들지도 기대지도 않는다는 것이다. 책도 같은 말을 한다.

> 사실 타입스크립트는 무결성을 달성하기 위해 만들어진 것이 아닙니다. 무결성 대신, 사용의 편의성과 함께 이미 존재하는 자바스크립트와의 호환성을 우선시합니다. (p.271)

그러니 타입 검사를 통과했다는 것은 안전하다는 판정이 아니라 **내가 적은 규칙끼리 앞뒤가 맞는다**는 판정이다. 그 규칙이 도메인과 맞는지, 런타임 값과 맞는지, 시간이 지나도 느슨해지지 않는지는 아무도 안 본다. 도메인과 맞는지는 앞의 다섯 질문이 맡는다. 남은 둘을 무엇으로 막는지가 여섯 번째 질문이다.

런타임 값과 맞는지. API 클라이언트의 이 한 줄이 그 자리다.

```ts
function interpret<T>(response: Response, body: unknown, clock: ReferenceClock | null): ApiResult<T> {
  const requestId = requestIdOf(response);

  if (response.ok) {
    return { ok: true, body: body as T, status: response.status, requestId, clock, lifetime: cacheLifetimeFrom(response.headers) };
  }

  if (isErrorResponse(body)) {
    return failed({ kind: "contract", error: body, status: response.status, retryAfterMs: retryAfterMsOf(response, clock) });
  }

  return failed({ kind: "malformed", status: response.status, requestId });
}
```

`response.json()`을 `unknown`으로 받은 것까지는 괜찮다. 그런데 결국 `body as T`로 단언하고, 이 한 줄 뒤로 애플리케이션 전체가 `Board`와 `LiveVehicles`를 믿고 돈다. 서버가 필드 하나를 빼먹거나 숫자를 문자열로 바꿔 보내도 컴파일러는 아무 말도 하지 않는다. 할 수가 없다. 타입은 컴파일이 끝나면 지워진다. 그러니 내가 공들여 짠 타입 파일은 서버와 나 사이의 약속을 적어 둔 문서이지, 그 약속이 지켜지는지 확인하는 장치가 아니다.

비대칭이 하나 있다. 같은 함수에서 실패 응답은 `isErrorResponse`라는 타입 가드로 런타임에 검사한다. 성공 응답은 단언한다. 실패 응답은 클라이언트 자신이 실패의 종류를 정해야 해서 검사가 필요했고, 성공 응답은 그대로 앱에 넘기면 되니 검사할 이유가 없었다. 검증은 위험한 곳이 아니라 필요가 생긴 곳에 생겼다. 앱에 넘기는 값이야말로 가장 넓게 퍼지는 값인데, 그 경계가 비어 있었다.

들어갈 것은 스키마다. 책은 타입 정보와 검증 로직을 따로 관리하는 것을 최악의 중복이라 부르고(p.426), 원천을 하나로 만드는 방법으로 zod를 든다.

```ts
const ObservationSchema = z.discriminatedUnion("state", [
  z.object({ state: z.literal("UNKNOWN"), observedAt: z.null(), staleAt: z.null() }),
  z.object({
    state: z.enum(["VEHICLES_PRESENT", "NO_VEHICLES_OBSERVED"]),
    observedAt: z.string(),
    staleAt: z.string(),
  }),
]);

export type Observation = z.infer<typeof ObservationSchema>;
```

첫 번째 질문에서 적은 판별 유니온과 같은 모양인데, 이제 타입이 스키마에서 나온다. 약속을 적는 문서와 약속을 확인하는 장치가 한 원천이 되니 둘이 어긋날 길이 없다. 클라이언트 변경은 크지 않다. 단언하던 자리에서 해석하고, 실패하면 이미 있는 실패 종류로 흘려보낸다.

```ts
type Decode<T> = (body: unknown) => T | null;

if (response.ok) {
  const decoded = decode(body);
  if (decoded === null) {
    return failed({ kind: "malformed", status: response.status, requestId });
  }
  return { ok: true, body: decoded, status: response.status, requestId, clock, lifetime: cacheLifetimeFrom(response.headers) };
}
```

`malformed`는 JSON이 깨졌을 때 쓰던 실패인데, 그 실패가 흘러가는 길이 이미 깔려 있다. 폴링 정책은 60초 뒤 다시 시도하고, 화면은 마지막으로 성공한 본문이 있으면 그것을 계속 그린다. 약속이 어긋난 응답을 화면까지 밀어 넣는 대신 검증된 직전 값을 보여 주며 다음 응답을 기다리는 동작이 코드 한 줄 없이 따라온다. 다만 JSON이 깨진 것과 JSON은 멀쩡한데 약속이 어긋난 것은 다른 사건이라 지표에서는 갈라 세어야 하고, 응답의 `requestId`를 같이 남겨야 서버 로그와 맞춰 볼 수 있다. 검증도 실행 중에 조용히 실패하면 타입이 없는 것과 같다. **검증 실패는 관측되어야 비로소 하한선이 된다.**

시간이 지나도 느슨해지지 않는지. 이것은 에이전트 시대에 새로 생긴 질문이다. 요즘은 코드를 혼자 다 쓰지 않는다. 에이전트가 타입 오류를 만나면 길이 둘인데, 코드를 고치거나 타입을 고치거나이고, 타입을 고치는 쪽이 거의 항상 더 짧다. `as`를 붙이거나, `!`를 붙이거나, 필드에 `?`를 붙이거나, `| null`을 더하거나. 전부 다섯 글자 안쪽이고 전부 컴파일을 통과시킨다. 사람도 급하면 그렇게 하는데, 에이전트는 급한 것이 기본값이다.

이미 세워 둔 것이 하나 있다.

```ts
// routeForecast.typeTest.ts

function rejectsSeatCountOnUnknown(): SeatInfo {
  const smuggled = { kind: "UNKNOWN" as const, remaining: 3 };
  // @ts-expect-error 좌석 모름(UNKNOWN)인데 remaining 값을 채우면 막혀야 한다
  const seat: SeatInfo = smuggled;
  return seat;
}

// 아래는 정상 코드다. kind로 분기하면 remaining이 number로 좁혀지는지 확인한다.
function narrowsSeatByKind(seat: SeatInfo): number {
  if (seat.kind === "EXACT") {
    return seat.remaining;
  }
  return 0;
}
```

일부러 틀린 코드를 써 두고 `@ts-expect-error`로 덮는다. 누군가 타입을 느슨하게 고쳐서 오류가 사라지면 이번에는 지시자 쪽이 기대한 오류가 없다고 오류를 내고, CI가 `tsc --noEmit`을 돌리니 거기서 걸린다. 책은 이것을 부정적 테스트라 부른다(p.326). 타입 검사는 규칙끼리의 정합성만 본다고 했는데, 이 테스트는 규칙이 느슨해지는 방향의 변경을 규칙끼리의 모순으로 바꿔 컴파일러가 보게 만든다. 정상 코드를 짝으로 두는 이유는 `@ts-expect-error`가 어떤 오류가 났는지는 따지지 않기 때문이다. 부정 테스트가 막혀야 할 것이 막힌다를 보고, 긍정 테스트가 열려야 할 것이 열린다를 본다.

그리고 어떤 길이 열려 있는지 프로젝트에서 세어 봤다.

| 우회로 | 지금 상태 | 막는 것 |
| --- | --- | --- |
| `any` | 막힘 | `no-explicit-any` (typescript-eslint recommended) |
| `@ts-ignore` | 막힘 | `ban-ts-comment` |
| `@ts-expect-error` | 설명이 있어야 통과 | `ban-ts-comment`의 allow-with-description |
| `as T` | 열림 | 없음. 클라이언트에 두 곳 |
| `!` | 열림 | 없음 |
| 필드에 `?`나 `\| null` 추가 | 특정 필드만 막힘 | `routeForecast.typeTest.ts` |

위 세 줄은 recommended 설정만으로 이미 닫혀 있었다. 열린 것은 단언 둘과 타입 자체를 느슨하게 만드는 길이다. 단언에는 순서가 있다. 런타임 검증이 들어가면 클라이언트의 `body as T`가 사라지고, 남는 `as`는 타입 가드 안의 하나뿐이라 그것도 스키마가 대신하면 프로젝트에서 단언이 0이 된다. 그때 단언을 린트로 금지할 수 있다. `consistent-type-assertions`를 `never`로 두면 되고, `as const`는 이 규칙이 예외로 둔다. 검증 없이 금지부터 하면 클라이언트가 컴파일이 안 되고, 결국 누군가 규칙에 예외를 뚫는다. **하한선은 위에서부터 조이는 것이 아니라 아래에 받침을 깔고 나서 조이는 것이다.**

사다리로는 이렇다. 타입 테스트는 느슨해지는 변경을 CI의 컴파일 오류로 올린다. 런타임 검증은 서버 계약 변경을 경계에서 잡는다. 관측이 없으면 경계에서 잡은 것이 아니라 어딘가에서 조용히 사라진 것이다.

여섯 질문을 한 표로 모으면 이렇다.

| 질문 | 안 던지면 | 던지면 | 도구 |
| --- | --- | --- | --- |
| 받아쓴 것인가, 적은 것인가 | 런타임 예외, 조용한 오류 | 만드는 줄 | 판별 유니온 |
| 원본과 함께 자라야 하는가 | 조용한 오류 | 만드는 줄, 파생 파일 | Pick, `satisfies Record`, `assertNever` |
| 깨질 생성 경로가 실제로 있는가 | 이동 없음, 비용만 | 대입 줄 | 생성부 수정, optional never |
| 오늘 어떤 호출부가 안전해지는가 | 이동 없음 | 발행하는 줄 | 사슬 검사 |
| 누가 이 값을 바꿀 수 있는가 | 런타임 예외 | 변경하는 줄 | `readonly`, 지역 변수 |
| 못 보는 자리는 무엇으로 막는가 | 런타임 예외, 조용한 오류 | CI, 런타임 경계 | 타입 테스트, 스키마, 관측 |

돌아보면 타입을 붙이는 사람과 설계하는 사람의 차이는 아는 문법의 수가 아니었다. 여섯 질문 중 새로운 문법을 요구하는 것은 하나도 없다. 차이는 타입을 적기 전에 다음 변경을 그려 보느냐, 그리고 그 변경이 터질 자리를 고르느냐에 있다. 유니온 글의 끝에 현실에서 가능한 상태는 그대로 담고 불가능한 상태만 담을 수 없게 만드는 것을 추구미로 적었는데, 여섯 질문을 지나고 나니 한 줄이 더 붙는다. **타입 설계는 다음 변경이 실패할 자리를 고르는 일이고, 좋은 설계는 그 자리를 가장 싼 곳까지 끌어올린다. 끌어올릴 수 없는 자리는 관측한다.**

에이전트 이야기로 끝내야겠다. 코드를 쓰는 손이 바뀌는 만큼 이 질문들은 덜 중요해지는 것이 아니라 더 또렷해진다. 에이전트는 문법이 허락하는 가장 짧은 표기를 고르는 데 나보다 빠르고, 그래서 질문을 안 던진 타입을 가장 먼저 느슨하게 만든다. 여섯 질문은 결국 사람이 남겨야 할 몫의 목록이다. 무엇을 적을지, 적을지 말지, 제대로 적어도 안 보이는 것을 무엇으로 볼지. 타입은 내가 적은 만큼만 지켜 주고, 그 "만큼"을 정하는 것이 설계다.
